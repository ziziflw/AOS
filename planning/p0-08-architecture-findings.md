# P0-08 最小扩展决策（实施前记录）

2026-10-29。当前任务已明确授权 P0-08 离线实施；此前 Reuse First 文档中的“未启动 P0-08”为历史范围。

原 C1 的最小反例：模型输入 900 Token、输出 100、maxOutputTokens=128。以 total=1000 回填旧 usage 会触发输出上限误报；只填 100 则漏计输入。响应丢失时旧 terminal 释放全部预留，不能表示未核实消耗。旧 cost 只准为零，是合成实验限制。

必要改动：原 Runtime 提取一个默认行为不变的 `_validate_usage` 钩子；P0-08 在可信 C1 子类中实现模型准入和结算，复用同一个 `_change`、SQLite事务、attempt、审批、调度和恢复。模型预留与 node-dispatched 原子提交；结算与 node-terminal 原子提交。无第二调度器或独立计费状态库。

模型节点维持 P0-02 executionKind=model / effect=billable，实验适配器命名 fixture.* 仅因使用自有 HTTP 服务。真实供应商未获收费授权，保持不可派发。能力只承诺固定实验模型/API版本，不能推及真实供应商全部模型。

对响应丢失、取消及进程中断，未知消耗保留额度；没有供应商核实接口时不支持重新派发或解冻额度。费用是显式合成费率下的估计，不是账单。

## 实施后的证据与仍需决策项

1. 原反例已由T18实际SDK响应复现并通过：总Token与输出上限分开。T09/T19说明预算预留必须覆盖并发和缺usage后的后续准入，不能只在完成时累计。
2. 模型业务终态和消耗确定性是两个维度：输出合法可以succeeded，同时usage未知并保留额度。unknown终态无法通过重新点击运行核实，下一阶段应优先提供有依据的核实/人工结算入口，不能自动解冻。
3. 原终态写入对billable取消的默认语义不足。P0-08可信C1子类对已派发模型统一保守unknown，不扩大旧合成节点语义；旧18/14/18/15/12方法和原19窗口步骤回归通过。
4. 两个费用字段属于过渡兼容：旧usage.costMinor保持旧合成语义，modelCosts是明确估算。它们在同一SQLite快照，不是两套状态权威，但正式API必须统一费用语义/版本，避免后续客户端把旧零字段误读为账单。
5. 在取得状态库锁之前创建凭据或写工作流清单会影响首个运行。P0-08已改为先认领，T20断言第二实例无法改清单或凭据；无需重写旧实验。
6. 原EnvironmentBinding没有http-loopback传输枚举。沿用P0-05可信程序解析约定，真实HTTP端口只在当前执行进程内部解析。通用HTTP服务接入应另提最小传输扩展，不能把明文测试HTTP当TLS证明。
7. 官方SDK升级到httpx2而原协议依赖仍用httpx；独立venv内并存及pip check通过。新major升级不能靠“官方”两字略过源码、依赖、取消和预算回归。
8. 当前复用P0-07宿主/前端自有胶水副本便于隔离，长期应提取共同宿主边界/配置入口以减少副本漂移；调度器没有复制。尚无迁移LangGraph/Temporal或冻结Python的证据。

完整运行、失败及未测范围见[p0-08-model-verification.md](p0-08-model-verification.md)。真实供应商能力、最终账单、缓存/推理Token、发行打包和Linux/macOS仍未验证。
